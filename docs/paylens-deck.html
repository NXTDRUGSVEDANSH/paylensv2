Where it deliberately departs

Technical decline is set to 1.5%, not NPCI's 0.24%. A dataset at the published rate has roughly 1,800 technical declines in four months — too few to decompose, rank or trend, so the product would have nothing to demonstrate on its most interesting path.
Every modelled share is labelled [MODELLED] or [ASSUMED] in datasets/CALIBRATION.md, with its source. An invented number presented as observed is the defect this whole product is built against.
Six related tables, and the arithmetic behind the claim
The schema
fact_transactions — one row per attempt
fact_settlements — payout batches
dim_merchant — tier, category, risk, region
dim_bank — issuer and acquirer, NPCI rates
dim_payment_method — rail, network, card type
dim_terminal — health, connectivity, estate
dim_failure_code — category, decline type, owner, journey step, whether it is worth retrying
Why a rate moved
delta = Σ(wₜ−wₖ)·vₖ   mix — traffic moved between segments
        + Σ wₜ·(vₜ−vₖ)   rate — segments changed their own rate
Measured here: −1.33pp overall, of which −1.23pp is mix and −0.09pp is rate — 92.9% traffic mix.
The identity is exact, so the residual is the test: 1.7e−15. If it does not close, the weights do not sum to one, and a split that does not balance is reported as a failure rather than as an answer.

Data quality — faults planted, then surfaced

PAYLENS
Five faults are planted in the data on purpose
Counting hazards
Duplicate txn_ids — a double-ingest window. Every honest query must de-duplicate or counts inflate silently.
Negative amounts — refund corrections posted against the original rail. They are included in totals, and said so.
Attribution hazards
2.09% of attempts carry no issuer. An issuer breakdown genuinely will not sum to the overall total.
Two sources disagree on attempt counts for 5 merchants — transactions versus settlements.
Window hazards
The last 2 days are part-ingested. A trend ending inside that window slopes down for a reason that has nothing to do with payments.
An earlier design trimmed the window and re-planned. PayLens reports it and leaves the query alone.
Five probes run against the window every answer actually used
CheckWhat it finds on this dataset
duplicate_txn_ids verifies the view's de-duplication held
null_issuer 2.09% — issuer rows will not sum
partial_days last 2 days under-ingested; reported, never trimmed
negative_amount refund corrections on the original rail
settlement_mismatch 5 merchants where the two sources disagree
Thresholds and wording live in views.yaml, next to the model, so the trip point and the sentence a reader sees are reviewed together.
Three rules these probes follow
Findings reach the reader, not just a tab. A failing probe is appended to the answer's caveats and deduplicated against what the prose already said — a warning nobody surfaces was not issued.
Every probe is a guarded query with the caller's own principal. A background query is the easiest place to leak rows a role may not see, because it is not user-initiated and so never looks like the thing to check.
The duplicate check verifies the guarantee, not the raw table. the allowlist blocks fact_* and that is not relaxed for a probe, so the check asserts no txn_id survives twice into the view — which fails loudly if de-duplication ever breaks.
When two sources disagree
The answer states the documented precedence (transactions are the system of record) and quantifies the gap. It never averages them and never quietly serves the larger: a reader handed one number is entitled to know the other existed.
What the reader actually sees when a probe fires
"2.09% of attempts in this window have no issuer_bank recorded. They are excluded from any issuer breakdown but counted in the overall total, so the segment rows will not sum to the total."
"The last 2 day(s) of this window are only partially ingested (41% of a typical day). Volume is understated and a downward trend at the right-hand edge may not be real."
"Transactions and settlements disagree on attempt counts for 5 merchant(s) in this window, worst M-1187 at 6.4%. Counted from v_attempts, which is the system of record."
These sentences are templates in views.yaml, filled from the probe's own result — not prose the model was asked to write. A caveat the model composes is a caveat it can forget.

Semantic model, the guard, and access control

PAYLENS
The view layer — what the model is allowed to see
v_attempts
One row per attempt, already de-duplicated (QUALIFY row_number() … = 1) and already joined to all five dimensions.
Joins disappear from the prompt, which removes the second largest class of text-to-SQL error — and the model cannot forget a de-duplication rule it never knew existed.
Indicator columns
is_success · is_failed · is_pending
is_resolved = SUCCESS or FAILED. PENDING is excluded deliberately — an attempt that has not resolved is not a failure, and counting it as one understates the rate.
is_business_decline · is_technical_decline — the customer's fault versus ours
Declared once, enforced everywhere
10 metrics
4 of them ratios
26 dimensions
14 decomposable
7 intents
4 roles
Format, synonyms, null labels and the canonical formula all live in views.yaml — so the prose speaks percent and rupees without the model doing arithmetic.
Fourteen checks stand between the model and the database
Check 10 — the backstop
10a views only — raw tables rejected
10b it parses
10c no SELECT * on a wide view
10d a column aliased with a metric id must use the official expression. successes / count(*) is plausible, readable, and silently a different number.
10e no rate grouped by a failure-only column. A real answer once read "the 'customer' failure owner has a 0% success rate on 19,784 attempts" — correct arithmetic, nonsense sentence, and it reads as a finding.
The nine guard checks
1 single statement · 2 SELECT only · 3 no injection
4 table allowlist · 5 column allowlist + masking
6 RBAC predicate injection · 7 row cap sentinel
8 cost estimate · 9 re-walk: the predicate survived
All checks work on the AST, never the SQL string. A DROP substring test misses /*x*/DROP.
The guard does not care who wrote the SQL. Model-authored queries pass the same checks compiled ones did.
The hole this design had to close
assert_injected skips tables a query does not name:
if not targets: continue  # vacuously passes
The classic model anchors every role scope on fact_transactions. A PayLens query reads v_attempts, names no fact_transactions, and would therefore get no row filter while check 9 passed anyway — a merchant reading every merchant's rows.
Fix: PayLens declares anchor_table: v_attempts. guard() is parameterised by the model it is handed, so enforcement is the same code pointed at a different target — not a second copy that could drift.
A test asserts the hole exists under the classic model and is closed under PayLens's, so nobody can simplify it back onto the classic model without a test going red.

Three properties worth stating
A missing claim refuses. An unscoped query is never the fallback when a claim is absent.
The filter is injected after the model writes. The prompt tells it not to add an access-control filter of its own — a filter the question asks for is the model's to write, a filter the viewer's permissions require is not.
Measured, not asserted. The evaluation strips the predicate from each scoped query and neutralises it with OR 1 = 1; check 9 must refuse both.

What the baseline is

Two model calls and nothing else. Call 1 writes SQL from the raw fact_* / dim_* DDL; call 2 narrates the rows it got back. Same model, same temperature, same questions.
No retrieval, no healing, no guard. No Chroma, no few-shots, no view layer, no check 10, no nine checks, no RBAC injection, no profiler, no grounding check.
Same 400 questions: 400 SQL calls, 217 narration calls — the other 183 produced no rows to narrate. Not a straw man: it is the shape most text-to-SQL systems ship in, and the same baseline the prior-art report used. The gap between the two columns is the price of the architecture, in the same units.

Four principles, stated as constraints
Python computes, the model picks. There is no calculator tool, because a number from a tool call has no provenance to show beside the answer.
The query is cached; the answer never is. A stored answer is a number that was true once, with no way to show a reader which of those two it is.
Advice is verified the way numbers are. "You should enable network tokenisation" contains no figure, so the grounding check waves it through — a second check drops any recommendation with no playbook behind it, and therefore no owner.
Never an industry benchmark as fact. Asked "is 86% good", the honest answer is that no benchmark is held here, and then a comparison against this estate's own best segment.
Known limits, stated first
PayLens needs a language model to author; with no key it refuses rather than guessing. Definitions and the decomposition have offline templates, so those two degrade rather than fail.
Conversation state lives in the browser — clearing site data loses the threads, and they do not follow you to another device.
Advisory coverage is exactly as wide as playbooks.yaml and no wider. A question no playbook covers degrades to a measurement rather than inventing counsel.
